# 微博

独立的 `Weibo Ad Filter` 模块，处理明确的广告数据并保留普通内容。

## 当前处理范围

| 位置 | 处理依据 |
| --- | --- |
| 开屏、预加载与广告缓存 | 已确认广告接口中的 `ads`、`cached_ad.ads` |
| 信息流、搜索与评论 | `mblogtype=1`、`is_ad`、`is_ad_card`、`ad_marked` 等明确标记，以及特定评论广告结构 |
| 热搜推广 | `is_ad_pos:1`、`cate_type:ads_hotword` 等独立字段或完整分隔标记 |
| 发现页轮播 | 角标文字明确为“广告”的卡片；保留同一轮播中的普通新闻 |
| 视频列表与预取缓存 | 识别 `svs` 等列表结构中的明确广告标记；保留普通视频和分页信息 |

`ad_state=1` **不能单独作为删除依据**：实际采样中正常视频也可能带有这个状态。普通推荐、商品话题、链接监测字段和无广告标记的博主内容不会仅因此被删除。

## 安装地址

```text
https://raw.githubusercontent.com/realyn/surge-ad-filters/main/apps/weibo/Weibo.sgmodule
```

安装步骤见[项目首页](../../README.md#安装)。模块仅追加以下 MitM 主机名，不使用全局通配符：

```text
api.weibo.cn
mapi.weibo.com
bootpreload.uve.weibo.com
bootrealtime.uve.weibo.com
sdkapp.uve.weibo.com
wbapp.uve.weibo.com
```

只有匹配指定接口的响应才会运行脚本。响应体上限为 2 MiB；超过上限时 Surge 会跳过脚本。无效 JSON、未知顶层结构和 HTTP 错误响应保持原样。异常时不返回部分修改结果。

同一响应只会执行首个匹配的响应脚本，因此应避免同时启用多个处理相同微博接口的模块。以上运行机制见 [Surge 响应脚本文档](https://manual.nssurge.com/scripting/http-response.html)。

## 适配与保留边界（v0.7.1）

- 开屏只匹配原有四个广告主机和接口路径，将 `/v1/`–`/v3/` 放宽为正整数版本 `/vN/`，仍要求识别到已知广告数组或开屏开关。
- 内容只处理列出的读取接口，支持实际观察到的 POST 读取；发布、删除、关注和私信等接口不纳入。不会整体拦截 `weibo.com` 或 `/2/`。
- 新卡片类别可使用 `is_ad` 等明确标记；仅在内容列表项的 `data`、`mblog`、`blog` 包装中检查最多三层。`mblogtype=1` 仅在已知内容语境中使用。
- 不重新序列化无关数值，保留原始长整数 ID、游标、字符串和分页。普通父容器不会仅因广告子项而整体删除。
- HTTP 错误、204/206、业务错误、重复 JSON 键、未知结构，以及超出深度或节点数限制的响应放行。若某个业务列表会被删空，保留该列表，可能因此留下广告；专用广告数组仍可清空。
- JSC、2 MiB 响应上限和 5 秒超时不变。诊断需显式添加 `argument=diagnostic`，只输出处理结果、删除计数、保护计数和耗时；正式模块默认关闭调试。

## 排查

1. 确认模块启用、MitM 证书受信任、外部脚本资源已下载。
2. 关闭其他匹配同一微博接口的响应脚本，再复现。
3. 仅在诊断时开启捕获，复现后及时关闭；检查请求是否经过 MitM、是否匹配脚本、是否超过响应体上限。
4. 如出现正常内容丢失，先停用本模块。反馈广告位置、应用版本和最小复现步骤即可；不要直接上传私人抓包。

离线使用时，可下载模块和 `weibo.js`，将模块中的 `script-path` 改为与主配置同目录下的本地脚本路径。这只涉及模块自身，无需编辑主配置。路径与缓存规则见 [Surge 脚本说明](https://manual.nssurge.com/scripting/overview.html)。
